# Контракт API «Служба поддержки»

Интерфейс учебного сервера, с которым работает клиент начиная с ПР4.
Составлен по образцу контракта учебного API «Библиотека» и повторяет все
его соглашения; отличается только предметной областью — вместо книг,
авторов и выдач здесь заявки, сотрудники поддержки, заявители, отделы
и категории.

Базовый адрес по умолчанию: `http://localhost:8080/api`

Запуск сервера:

```
node api/mock-server.js --port 8080 --origin http://localhost:5555,http://127.0.0.1:5555
```

Начальный набор берётся из `api/seed.json`. Файл порождается из того же
кода, что заполнял хранилище браузера в ПР3:

```
dart run tool/dump_seed.dart
```

## 1. Общие соглашения

- Формат обмена — JSON, кодировка UTF-8.
- Заголовок `Content-Type: application/json` обязателен для запросов с телом.
- Идентификаторы целочисленные, начинаются с 1.
- Даты передаются строкой в формате ISO 8601.
- Все ответы со списками возвращают одинаковую оболочку с постраничной
  разбивкой.

### 1.1. Оболочка списка

```json
{
  "items": [ /* массив объектов */ ],
  "page": 1,
  "size": 10,
  "total": 26,
  "totalPages": 3
}
```

### 1.2. Формат ошибки

| Код | Смысл | Тело |
|---|---|---|
| 400 | Некорректный запрос | `{ "message": "..." }` |
| 401 | Не аутентифицирован либо токен истёк | `{ "message": "..." }` |
| 403 | Роль не имеет права на операцию | `{ "message": "..." }` |
| 404 | Объект не найден | `{ "message": "..." }` |
| 409 | Конфликт: нарушено ограничение целостности | `{ "message": "..." }` |
| 422 | Ошибка валидации полей | см. ниже |
| 500 | Внутренняя ошибка сервера | `{ "message": "..." }` |

Тело ответа 422:

```json
{
  "message": "Ошибка валидации",
  "errors": {
    "number": "Заявка с номером SD-000001 уже зарегистрирована",
    "account.login": "Логин ivanov уже занят"
  }
}
```

Ключи объекта `errors` совпадают с именами полей формы, включая вложенные:
`account.login` — путь до поля внутри группы. Это позволяет показать
ошибку прямо в соответствующем поле без сопоставления вручную.

Коды 401 и 403 сервер выдаёт начиная с ПР5: все адреса, кроме
`/api/auth/*` и служебных, требуют заголовок `Authorization`, а права
ролей описаны в разделе 8.

## 2. Ресурсы

Единообразный набор операций доступен для `tickets`, `employees`,
`requesters`, `departments`, `categories`. Ниже показан на примере заявок.

### `GET /api/tickets`

| Параметр | Тип | Назначение |
|---|---|---|
| `search` | строка | поиск по номеру и теме, регистр не учитывается |
| `categoryId` | число | фильтр по категории |
| `priority` | строка | `low`, `normal`, `high`, `critical` |
| `status` | строка | `new`, `in_progress`, `waiting`, `resolved`, `closed` |
| `assigneeId` | число | исполнитель либо соисполнитель |
| `requesterId` | число | заявитель |
| `createdFrom`, `createdTo` | дата | диапазон даты регистрации, границы включаются |
| `sort` | строка | поле и направление, например `dueAt,asc` |
| `page` | число | номер страницы, с 1 |
| `size` | число | размер страницы, по умолчанию 10, максимум 100 |
| `includeDeleted` | `true`/`false` | включать логически удалённые |

Пример: `GET /api/tickets?search=принтер&categoryId=3&sort=dueAt,asc&page=2&size=10`

Параметры отбора остальных коллекций:

| Коллекция | Поиск по | Фильтры | Сортировка |
|---|---|---|---|
| `employees` | фамилия, должность | `departmentId`, `categoryId`, `supportLine`, `active` | `fullName`, `position`, `supportLine`, `email` |
| `requesters` | фамилия, логин | `departmentId`, `blocked` | `fullName`, `position`, `login` |
| `departments` | название, код | — | `name`, `code`, `location` |
| `categories` | название, описание | `active` | `name`, `slaHours` |

### `GET /api/tickets/{id}`

Ответ `200` — объект заявки, `404` — если записи нет.

### `POST /api/tickets`

Тело — представление на запись (см. раздел 3). Ответ `201` — созданный
объект с присвоенным `id`.

### `PUT /api/tickets/{id}`

Тело такое же, как у `POST`. Ответ `200`.

### `DELETE /api/tickets/{id}`

Логическое удаление: объект получает `deletedAt` и перестаёт попадать
в выборки. Ответ `204`. Если на запись ссылаются другие — `409`.

### `DELETE /api/tickets/{id}?hard=true`

Физическое удаление, запись стирается безвозвратно. Ответ `204`.
Проверка ссылок выполняется так же, как при логическом удалении:
удалённый отдел исчез бы из выпадающих списков, а ссылки на него
остались бы.

### `POST /api/tickets/bulk-delete`

Множественное удаление. Тело: `{ "ids": [3, 7, 11] }`. Ответ `200`:
`{ "deleted": 3 }`. Сначала проверяются все выбранные записи и только
потом удаляется хоть одна: иначе при отказе на середине списка часть
записей оказалась бы удалена, а клиент увидел бы только ошибку.

### `POST /api/tickets/{id}/restore`

Восстановление логически удалённой записи. Ответ `200`.

### `GET /api/tickets/next-number`

Свободный регистрационный номер. Ответ `200`: `{ "number": "SD-000027" }`.
Адрес разбирается раньше адреса записи, иначе `next-number` было бы
принято за идентификатор.

### Служебные адреса

| Адрес | Назначение |
|---|---|
| `GET /api/__health` | проверка, что сервер отвечает; возвращает размеры коллекций и список разрешённых источников |
| `POST /api/__reset` | вернуть начальный набор |
| `?__delay=1500` | задержка ответа в миллисекундах |
| `?__fail=500` | принудительный код ошибки |

## 3. Модели

Представление на чтение и на запись различаются. На запись уходят
идентификаторы связей, на чтение приходят развёрнутые объекты и счётчики
связанных записей.

### `Ticket` — заявка

Чтение:

```json
{
  "id": 1,
  "number": "SD-000001",
  "subject": "Не включается системный блок",
  "description": "При нажатии кнопки питания индикаторы не загораются.",
  "category": { "id": 1, "name": "Оборудование" },
  "priority": "high",
  "status": "in_progress",
  "assignee": { "id": 1, "fullName": "Абрамов Кирилл Сергеевич" },
  "coworkers": [ { "id": 4, "fullName": "Гордеева Мария Ивановна" } ],
  "requester": { "id": 1, "fullName": "Семёнов Артём Владимирович" },
  "createdAt": "2026-08-03T09:12:00.000",
  "dueAt": "2026-08-05T18:00:00.000",
  "deletedAt": null
}
```

Запись: `number`, `subject`, `description`, `categoryId`, `priority`,
`status`, `assigneeId`, `coworkerIds`, `requesterId`, `createdAt`, `dueAt`.

### `Employee` — сотрудник поддержки

```json
{
  "id": 1,
  "fullName": "Абрамов Кирилл Сергеевич",
  "position": "Инженер поддержки",
  "department": { "id": 1, "name": "Отдел технической поддержки" },
  "email": "abramov@sd.local",
  "phone": "+7 495 000-10-01",
  "supportLine": 1,
  "categories": [ { "id": 1, "name": "Оборудование" } ],
  "isActive": true,
  "deletedAt": null,
  "ticketCount": 4
}
```

Запись: `fullName`, `position`, `departmentId`, `email`, `phone`,
`supportLine`, `categoryIds`, `isActive`.

### `Requester` — заявитель

```json
{
  "id": 1,
  "fullName": "Семёнов Артём Владимирович",
  "position": "Экономист",
  "department": { "id": 5, "name": "Планово-экономический отдел" },
  "account": {
    "login": "semenov.av",
    "email": "semenov@corp.local",
    "phone": "+7 495 000-30-11",
    "office": "Корпус Б, каб. 201",
    "isBlocked": false
  },
  "note": "",
  "deletedAt": null,
  "ticketCount": 2
}
```

Учётная запись — связь один к одному, отдельного адреса у неё нет:
она создаётся и меняется вместе с заявителем.

### `Department` — отдел

```json
{
  "id": 1,
  "name": "Отдел технической поддержки",
  "code": "ITSUP",
  "location": "Корпус А, каб. 104",
  "phone": "+7 495 000-10-00",
  "deletedAt": null,
  "employeeCount": 6,
  "requesterCount": 0
}
```

### `TicketCategory` — категория заявок

```json
{
  "id": 1,
  "name": "Оборудование",
  "description": "Неисправности компьютеров, мониторов, периферии.",
  "slaHours": 24,
  "isActive": true,
  "deletedAt": null,
  "ticketCount": 6,
  "employeeCount": 5
}
```

## 4. Схема данных

```
Department 1 ──< M Employee M >──< M TicketCategory
Department 1 ──< M Requester
Requester  1 ── 1 ServiceAccount
Requester  1 ──< M Ticket
TicketCategory 1 ──< M Ticket
Employee   1 ──< M Ticket            (исполнитель)
Employee   M >──< M Ticket           (соисполнители)
```

Связи:

- `Department` → `Employee`, `Department` → `Requester`: один ко многим;
- `TicketCategory` → `Ticket`, `Requester` → `Ticket`: один ко многим;
- `Employee` ↔ `TicketCategory`: многие ко многим (обслуживаемые категории);
- `Employee` ↔ `Ticket`: многие ко многим (соисполнители);
- `Requester` ↔ `ServiceAccount`: один к одному.

## 5. Проверка полей на сервере

Сервер повторяет проверки клиента и добавляет те, которые клиент
выполнить не может: уникальность, существование связанных записей
и правила, связывающие два поля.

| Сущность | Уникально | Существование ссылки | Правило предметной области |
|---|---|---|---|
| `tickets` | `number` | `categoryId`, `requesterId`, `assigneeId`, `coworkerIds` | исполнитель обязан обслуживать категорию заявки; `dueAt` не раньше `createdAt` |
| `employees` | `email` | `departmentId`, `categoryIds` | линия поддержки 1–3 |
| `requesters` | `account.login`, `account.email` | `departmentId` | — |
| `departments` | `name`, `code` | — | код — заглавная латиница и цифры |
| `categories` | `name` | — | норматив 1–720 часов |

## 6. Отказ в удалении

| Удаляемая запись | Что проверяется |
|---|---|
| Отдел | сотрудники, заявители |
| Категория | заявки, компетенции сотрудников |
| Сотрудник | заявки — и назначение, и соисполнение |
| Заявитель | заявки |

Уже удалённые записи в счёт не идут. Сообщение собирается сервером
целиком: `Нельзя удалить: отдел «Отдел технической поддержки».
Связанные записи: 6 сотрудников`.

## 7. Доступ с другого источника

Сервер отдаёт на каждый ответ:

```
Access-Control-Allow-Origin: <адрес клиента, если он в списке разрешённых>
Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400
```

Отдельно обработан метод `OPTIONS` на всех адресах: браузер отправляет
предварительный запрос перед любым обращением с заголовком
`Authorization` или методом, отличным от `GET` и `POST`. Ответ — `204`
с теми же заголовками.

`http://localhost:5555` и `http://127.0.0.1:5555` — с точки зрения
браузера разные источники, поэтому в списке разрешённых должны быть оба.

## 8. Вход в систему и роли

Добавлено в ПР5 по образцу раздела 2 контракта «Библиотека».

Запуск с коротким сроком жизни токена — для проверки обновления:

```
node api/mock-server.js --port 8080 --ttl 60
```

| Параметр | Смысл | По умолчанию |
|---|---|---|
| `--ttl` | срок жизни токена доступа, с | 900 |
| `--refresh-ttl` | срок жизни токена обновления, с | 604800 (неделя) |

Токен состоит из полезной нагрузки в base64url и подписи HMAC-SHA256.
Клиент может прочитать нагрузку, но не может изменить её так, чтобы
подпись сошлась. Токены обновления одноразовые и хранятся в памяти
сервера: после перезапуска ни один из выданных ранее не действует.

### `POST /api/auth/register`

```json
{ "username": "petrov.pi", "password": "Passw0rd!", "email": "petrov@corp.local", "fullName": "Петров Пётр Ильич" }
```

Ответ `201`: пользователь без пароля. Роль всегда `requester`, поле
`role` в теле игнорируется. Если карточка заявителя с таким доменным
логином уже заведена и ни с кем не связана, пользователь связывается
с ней; иначе заводится новая.

Ошибки `422`: `username` — формат и занятость, `fullName`, `email`,
`password` — не короче восьми символов, цифра, специальный символ.

### `POST /api/auth/login`

```json
{ "username": "grigorev", "password": "grigorev123" }
```

Ответ `200`:

```json
{
  "accessToken": "eyJzdWIiOjMsInJvbGUiOi...",
  "refreshToken": "eyJzdWIiOjMsInR5cGUiOi...",
  "expiresIn": 900,
  "user": {
    "id": 3, "username": "grigorev", "fullName": "Григорьев Пётр Петрович",
    "email": "grigorev@corp.local", "role": "requester",
    "employee": null, "requester": { "id": 8, "fullName": "Григорьев Пётр Петрович" }
  }
}
```

Неверный логин и неверный пароль дают одно и то же сообщение
`401 Неверный логин или пароль`: по ответу нельзя узнать, какие логины
существуют.

### `POST /api/auth/refresh`

Запрос `{ "refreshToken": "..." }`. Ответ — новая пара токенов
в формате входа. Предъявленный токен обновления отзывается; повторное
его предъявление — `401`.

### `GET /api/auth/me`

Текущий пользователь по заголовку `Authorization: Bearer <accessToken>`.

### `POST /api/auth/logout`

Запрос `{ "refreshToken": "..." }`, ответ `204`. Токен обновления
отзывается; токен доступа доживает свой срок.

### 8.1. Учётные записи для проверки

| Логин | Пароль | Роль | Связь |
|---|---|---|---|
| `grigorev` | `grigorev123` | `requester` — заявитель | карточка заявителя 8 |
| `abramov` | `abramov123` | `agent` — специалист поддержки | сотрудник поддержки 1 |
| `admin` | `admin123` | `admin` — администратор | — |

### 8.2. Права ролей

Роль берётся из записи пользователя на сервере по идентификатору
из подписанного токена, а не из данных, присланных клиентом.

| Операция | requester | agent | admin |
|---|---|---|---|
| Собственные заявки: просмотр, подача обращения, возврат решённой в работу | да | нет | нет |
| Личная очередь исполнителя | нет | да | нет |
| Журнал заявок: просмотр | нет | да | да |
| Заявки: регистрация, изменение, логическое удаление | нет | да | нет |
| Заявители: просмотр | нет | да | да |
| Заявители: создание, изменение, логическое удаление | нет | да | нет |
| Сотрудники поддержки: просмотр | нет | да | да |
| Сотрудники поддержки: создание, изменение, логическое удаление | нет | нет | да |
| Отделы: просмотр | нет | да | да |
| Отделы: создание, изменение, логическое удаление | нет | да | нет |
| Категории: просмотр | да | да | да |
| Категории: создание, изменение, логическое удаление | нет | да | нет |
| Физическое удаление (`?hard=true`) | нет | нет | да |
| Восстановление (`/restore`) | нет | нет | да |
| Пользователи и роли | нет | нет | да |
| Статистика | нет | нет | да |

Отказ по правам — `403` с текстом вида `Недостаточно прав: операция
«физическое удаление записей» недоступна роли «Специалист поддержки»`.

### 8.3. Адреса ролей

| Адрес | Право | Назначение |
|---|---|---|
| `GET /api/my/tickets` | `ownTickets.view` | заявки, где заявитель — связанная карточка |
| `POST /api/my/tickets` | `ownTickets.create` | обращение: `subject`, `description`, `categoryId`, `priority` (`low`, `normal`, `high`); номер, статус, заявителя и срок назначает сервер |
| `POST /api/my/tickets/{id}/reopen` | `ownTickets.reopen` | решённая заявка возвращается в работу; чужая заявка — `404`, нерешённая — `409` |
| `GET /api/my/queue` | `queue.view` | незакрытые заявки, где связанный сотрудник — исполнитель или соисполнитель |
| `GET /api/users` | `users.manage` | пользователи |
| `PUT /api/users/{id}` | `users.manage` | `{ "role": "agent" }`; собственную роль изменить нельзя — `409` |
| `GET /api/stats` | `stats.view` | заявки по статусам, приоритетам и категориям, просроченные, удалённые записи, пользователи по ролям |
